# PdfCraft implementation research

Research date: 2026-10-12. The audited source is [storytold/pdfcraft at `7163ba3dee8becfff6871c9a65d0d8314314742b`](https://github.com/storytold/pdfcraft/tree/7163ba3dee8becfff6871c9a65d0d8314314742b), cloned into a separate temporary research checkout. Findings below come from implementation files, manifests, attribution records, and CI definitions. This was a source audit; PdfCraft was not built, benchmarked, or manually exercised. Its tests were inspected, not executed.

## Architecture and implementation evidence

Paths below resolve against that immutable source revision.

| Area | Actual implementation | Lesson and limitation for this rewrite |
| --- | --- | --- |
| Workspace | [Cargo.toml](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/Cargo.toml) divides object parsing, filters, cryptography, typed model, rendering, fonts, content, editing, organizing, annotations, forms, redaction, signing, OCR, comparison, preflight, engine, platform, UI, and automation into crates. Edition 2024; workspace MSRV 1.95; own crates forbid unsafe code. | Keep headless engine independent of GUI. Do not reproduce thirty crates before they have a real caller. An unsafe-code lint does not make dependencies or malformed inputs safe. |
| Parsing and object model | [cos/src/document.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/cos/src/document.rs) owns original bytes through `Arc`, cross-reference entries, revisions, caches, and a copy-on-write edit overlay. It reads table/stream/hybrid cross-references and object streams; supports damaged-index reconstruction. [model/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/model/src/lib.rs) provides typed views and inherited page attributes. | PdfCraft has its own COS model; it is not simply an egui wrapper around lopdf. The source explicitly leaves memory-budgeted streaming and linearized output unfinished. Start with a tested lopdf adapter and retain a future boundary for lazy parsing. |
| Rendering | [render/src/raster.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/render/src/raster.rs) uses hayro interpretation/rasterization, parser reuse, render statistics, page/text requests, tiles, generation tracking, worker queues, watchdogs, and cooperative cancellation. Its declared hard caps are 8192 pixels per side and 64 million pixels per page. | CPU PDF rasterization and GUI GPU texture presentation are separate jobs. A bounded worker pool, stale-generation rejection, and explicit pixel budgets matter more than a dependency labeled GPU. These constants are evidence of PdfCraft's controls, not recommended defaults for our memory budget. |
| Fonts | [fonts/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/fonts/src/lib.rs) contains approximate Helvetica width helpers, encodings, font embedding, and script-specific APIs. [fonts/Cargo.toml](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/fonts/Cargo.toml) selects skrifa, harfrust, and unicode-bidi; [source_shaping.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/fonts/src/source_shaping.rs) handles source-font shaping. | Approximate metrics are not sufficient for arbitrary existing-text replacement. Glyph encoding, embedded subsets, ToUnicode mappings, bidi, shaping, and writing direction need separate proof. PdfCraft currently uses harfrust here, not rustybuzz. |
| Content editing | [edit/src/text.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/edit/src/text.rs) inventories lines and implements `replace_line`; [objects.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/edit/src/objects.rs), [images.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/edit/src/images.rs), and [added.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/edit/src/added.rs) distinguish original objects and additions. Page marks isolate graphics state and use marked-content artifacts. | Adding an overlay and replacing original content must remain different capabilities. Source content rewriting has stronger correctness requirements than drawing on top of a page. |
| Annotations and pages | [annot/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/annot/src/lib.rs) and [organize/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/organize/src/lib.rs) implement separate object-graph operations rather than UI-only actions. | Page edits must preserve inherited resources, links, field widgets, destinations, outlines, and document-level structures; concatenating page IDs alone is insufficient. |
| Forms | [forms/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/forms/src/lib.rs) walks inherited AcroForm field properties; creates text/choice appearances and switches checkbox/radio states. Authoring, scripting interfaces, detection, and appearance generation are separate modules. XFA has a separate crate. | Writing `/V` alone can leave a visually stale form. Module-level introductory comments still mention script work as unfinished while scripting modules exist: inspect functions instead of treating introductory status prose as definitive coverage. |
| Encryption and scripts | [crypt/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/crypt/src/lib.rs) implements standard-handler revisions R2–R6, passwords, permissions, crypt filters, and per-object keys. [js/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/js/src/lib.rs) has source-size/nesting refusal and Boa loop/recursion limits. | Authentication, permissions, algorithm support, signed-document integrity, and embedded code are separate trust boundaries. The first Rust milestone should reject unsupported encrypted/signed mutations and never run document JavaScript. Do not implement new PDF crypto from scratch. |
| Real redaction | [redact/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/redact/src/lib.rs) removes glyphs/images/paths, rewrites shared Form XObjects, removes overlapping annotations/widgets, and verifies residue. It contains an explicit `VerticalText` refusal. [interp.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/redact/src/interp.rs) and [sanitize.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/redact/src/sanitize.rs) implement content interpretation and sanitation. | A black rectangle is never secure redaction. Unsupported content must fail closed. Verification must inspect saved output, not only the in-memory edited stream. |
| Undo and saving | [engine/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/engine/src/lib.rs) keeps COS snapshots and undo/redo stacks. `save_bytes` writes incrementally; `save_full_bytes` refuses signed documents. [cos/src/writer.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/cos/src/writer.rs) falls back to a full rewrite for repaired cross-reference chains, encryption changes, and `full_save_required`. Full output visits reachable objects. | Incremental output retains old revisions: never use it for redaction/privacy erasure. Snapshot history is cheap only because its model shares unchanged data. Full cloned lopdf documents require a strict history budget. |
| Recovery | [ui-egui/src/recovery.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/ui-egui/src/recovery.rs) writes dirty working PDFs and JSON metadata every 60 seconds, reopens damaged/missing-metadata entries, and cleans saved/discarded entries. Protected working bytes stay encrypted; web recovery is explicitly absent. | Recovery records themselves contain private paths and document data. Use local private storage, test interrupted writes, and do not silently turn encrypted recovery into plaintext. |
| Native GUI | [apps/pdfcraft/src/main.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/apps/pdfcraft/src/main.rs) starts an eframe/egui application, native file integration, portable settings, platform-specific events, and an optional authenticated UI control channel. Shared craft-ui is pinned to an immutable Git revision. | A true native GUI does not need a local HTTP service or browser. Its platform work, fonts, accessibility, focus, IME, high-DPI behavior, and file dialogs are real engineering effort rather than a theme change. |
| CLI | [apps/pdfcraft-cli/src/main.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/apps/pdfcraft-cli/src/main.rs) exposes info/render/text/edit/combine/extract/split/audit, schema-backed automation, optional stdio MCP, and a `check` harness. Each corpus check runs in a separate child with a timeout. | Share engine semantics between CLI and desktop. Child-process timeout coverage is stronger than catching thread panics; allocation aborts and hung foreign/native code can escape an in-process guard. |
| OCR | [ocr/src/lib.rs](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/crates/ocr/src/lib.rs) uses ocrs/rten and separately fetched models, then adds invisible text over existing images. The source documents an English/Latin alphabet model and accent limitations. | A Rust OCR engine is not automatically multilingual or asset-license-free. Tesseract remains an optional local native capability candidate; searchable-PDF placement needs geometry and reading-order tests. |
| Tests and performance | Engine/forms/crypt/redact/edit/filter tests, proptest cases, rendering bounds tests, render work counters, corpus/fuzz xtasks, and [ci.yml](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/.github/workflows/ci.yml) exist. Normal CI covers Linux/Windows; macOS is reserved for release builds in that file. | These are inspected controls, not reproduced passing results or measured performance. Our own corpus needs rotated/cropped pages, inherited resources, Type3/CID fonts, encrypted objects, malformed cross-references, recursive graphs, oversized images, and signed files. |
| Packaging | [packaging](https://github.com/storytold/pdfcraft/tree/7163ba3dee8becfff6871c9a65d0d8314314742b/packaging) contains Windows MSI/security-audit/signing, Linux package/Flatpak definitions, FreeBSD packaging, icon generation, and platform assets. Release/packaging/FreeBSD/Windows ARM64 workflows are present. | Source-level packaging scripts do not prove shipped artifacts, signatures, or runtime compatibility. Each target needs build/install/open/save/uninstall evidence. |

## Licensing and copying boundary

The workspace declares **MIT OR Apache-2.0** and includes [LICENSE-MIT](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/LICENSE-MIT), [LICENSE-APACHE](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/LICENSE-APACHE), and [NOTICE](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/NOTICE). Source reuse is possible under the applicable terms, with notices retained and changes identified where required. No PdfCraft implementation or bundled assets were copied during this research.

[ATTRIBUTION.md](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/ATTRIBUTION.md) and `ATTRIBUTION.toml` separately record fonts, icons, models, brand assets, and dependency-bundled resources. The OCR model license is documented as CC-BY-SA-4.0, while application source is permissive. Font assets carry OFL and other notices. Brand graphics have a separate license file. Never infer an asset's license from the workspace manifest; source and model attribution obligations must be checked independently.

## Upstream patches are part of the observed product

[vendor/README.md](https://github.com/storytold/pdfcraft/blob/7163ba3dee8becfff6871c9a65d0d8314314742b/vendor/README.md) documents patched hayro, hayro-interpret, hayro-syntax, hayro-jbig2, lopdf, winit, and egui-wgpu. Examples include annotation appearance-state fixes, limits for self-referencing Type3/pattern paints, CID-width ranges, oversized masks/images, shared nested-paint budgets, font-parser fixes, and IME behavior.

Consequently, selecting the same crate names or versions does **not** reproduce PdfCraft's correctness, security bounds, or rendering fidelity. Before adopting a reported fix, check whether the upstream release already contains it, retain a minimal regression PDF with license provenance, and evaluate our exact locked dependency. Avoid adopting the entire vendor tree as a shortcut.

## Conclusions for PDF Editor Offline

Use PdfCraft as an implementation reference for boundaries and failure handling. Begin with independently written, fixture-tested Rust document operations and a native viewer on shared Rust engine semantics. Keep difficult text rewriting, signatures, AcroForm appearances, XFA, OCR, and irreversible redaction explicitly tracked in the migration matrix. A working viewer and page CLI are milestones; they do not establish feature parity or replacement of every legacy workflow.
