# Original text font-face changes

The current core supports genuine font changes on the existing editor's eligible
final `Tj` runs. `PdfDocument::change_content_text_face` selects one of the twelve
standard Courier, Helvetica or Times faces. It adds an isolated font resource to
the selected page and changes the font used by the original show operation.
This operation does not add an overlay or cover the old glyphs with artwork.

Each `ContentTextFaceChange` carries the source run identity and exact expected
text, a target `ContentTextFont`, an optional replacement and an explicit layout
policy. The target uses `WinAnsiEncoding` with printable ASCII only. With no
replacement, the original string token, including its escapes, stays byte exact.
The original font-size token, text matrix, spacing, horizontal scale and rise are
retained. A changed face naturally changes glyph ink and often line width.

The default policy preserves each word's nominal advance and the advance of
spaces. A request that changes these advances must explicitly choose
`AllowWidthChange`. This permits a different bounded line width; it does not wrap,
fit or reflow paragraphs and does not guarantee that new ink fits inside old ink.
The selected run is the final show immediately before `ET`, so no later show in
that text object depends on its new advance. Original persistent setters replay
after the isolated edit so later text objects and artwork retain their source
state.

The writer splices original decoded bytes. Unchanged numeric tokens, comments,
resources and other page objects remain intact; shared streams and resource
dictionaries are not edited in place. Standard-font results remain eligible for
subsequent supported text, size, position, color and face edits after a fresh
source-bound inventory. Stale, signed, encrypted, tagged, custom-font and complex
graphics-state sources fail before publication. Existing stream, operator, text,
object and serialized-document budgets remain enforced.

Core tests exercise all twelve target faces, independent qpdf 12.4.2 structural
checks and Poppler 26.10.0 extraction, nominal metrics and raster comparisons.
The references separately verify later inherited text, artwork and the shared
page. Exact unrelated-object assertions exempt only transport XRef streams
regenerated by the existing writer. There is no claim of identical glyph artwork
across renderers. Old source streams remain recoverable: font editing is not
redaction or secure erasure.

The CLI exposes `set-content-text-font INPUT --page 1 --operation N
--source-sha256 HASH --expected Original --font Times-Italic
--allow-width-change -o NEW.pdf`, with optional `--replacement`, `--dry-run`
and `--json`. Discover the hash and zero-based operation with
`inspect-content-text`. Invalid/stale requests and existing output files publish
nothing. The path-free worker accepts typed `ContentTextFace` changes plus a
whole-source fingerprint; it returns a verified PDF only after the transaction.

The native existing-text dialog has a **Font face** mode with a scrollable
twelve-face selector, explicit width-change acknowledgment and nominal advance.
It applies through the same worker, with one durable history commit, Undo/Redo
and verified Save As. Fresh inventory can edit the result again. Font/value/
property drafts are separate, guarded during close/quit/recovery. Tests exercise
actual controls, source/tab/page/revision checks, pending saves, child failures,
journal failure and independent saved-output extraction/raster comparisons.

User-selected embedded fonts and repeated editing of their emitted spans are a
separate unfinished tier. Manual native interaction and platform runtime evidence
for this new mode remain separate gates; no screenshots or release claims are
inferred from headless tests.
